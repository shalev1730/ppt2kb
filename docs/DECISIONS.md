# Implementation decisions

Recorded so reviewers understand *why* the solution looks the way it does and
where to extend it.

## What was reused from ppt2desc

* The conversion pipeline shape (PPT → PDF with LibreOffice → one PNG per page,
  fitted on a 1920×1080 canvas) and its code, hardened.
* The OpenAI-compatible request format (text part + base64 `image_url` data
  URI), the defensive response-content extraction, the thread-pool + rate
  limiter model for describing slides concurrently, and the intermediate
  results / resume idea (now persisted per slide in SQLite instead of partial
  JSON files).
* The `DeckData` / `SlideData` JSON schema (`deck`, `model`, `slides[].number`,
  `slides[].content`) — the JSON export remains readable by anything that
  consumed ppt2desc output; new fields are additive.
* The base prompt (kept as `BASE_PROMPT`) extended into a structured,
  bilingual, anti-hallucination system prompt.

What was dropped: all cloud LLM clients, the separate LibreOffice HTTP
container (replaced by in-process isolation), PyMuPDF (AGPL), `tqdm`/CLI
progress bars (replaced by the UI), `uv`-specific tooling.

## Architecture choices

| Decision | Alternatives considered | Reason |
|---|---|---|
| Single Python process: FastAPI + background worker threads + SQLite | Celery/Redis, n8n, separate converter service | Fewest moving parts for an air-gapped install; one unit to secure and monitor; 60-slide decks process in seconds against the model's latency, not CPU. `PPT2KB_MAX_CONCURRENT_JOBS` and `QWEN_CONCURRENCY` give enough parallelism. |
| `httpx` instead of the `openai` SDK | openai SDK with `base_url` | Full control of TLS (custom CA, mTLS), an outbound allow-list at transport level, no hidden defaults (api.openai.com, proxy env), smaller offline bundle. |
| Vanilla JS UI with no build step | React/Vite SPA | Nothing to download at build time, nothing served from CDNs, trivially auditable (3 static files), CSP `default-src 'self'`. i18n via a dictionary; RTL via `dir` on `<html>` + logical CSS properties. |
| `pypdfium2` for rasterising | PyMuPDF, pdf2image/poppler | Permissive license, pure wheel with bundled pdfium (no extra OS packages), fast. |
| Conversion isolation with rlimits + throw-away profile + process group kill | firejail/bubblewrap, separate container | Works identically in the container and on a plain server with no extra privileges; kernel-level sandboxing can be added on top (seccomp/AppArmor; the Compose file already drops all capabilities). |
| Credentials only from env/env file; UI secrets in memory | storing encrypted in SQLite | Keeps secrets in one well-known file with OS permissions; avoids inventing key management. `PPT2KB_PERSIST_UI_SECRETS` exists for labs. |
| Article HTML generated from escaped plain text, not from model HTML | let the model emit HTML / use a sanitizer | A fixed tag set generated by us cannot carry scripts, event handlers or external references; ServiceNow's editor can still be used after creation for richer formatting. |
| Images attached to the article and referenced via `/sys_attachment.do?sys_id=` | `db_image`, base64 inline images, external image server | Standard knowledge-article pattern, access follows the article record, no new tables, works in both the classic UI and Service Portal, indexed article text stays clean. |
| One article per presentation, idempotent by a hidden marker + local record | numbers in `short_description`, custom field | No custom fields needed (requirement); the marker is invisible to readers and searchable through the Table API; local record makes the common path fast. |
| Structured JSON from the model with a plain-text fallback | free text only | Gives the article title / visible text / procedures / uncertainties as separate, editable blocks and makes "do not invent" and "unreadable content" explicit; the fallback keeps endpoints without JSON mode working. |
| Extracted PPTX text passed to the model as a *hint* | image only | Improves transcription accuracy (especially Hebrew) at zero risk: the prompt states the image is authoritative, the hint is capped at 4 kB and clearly delimited. |

## Extension points

* **Topic-based splitting into several articles**: `publish_job()` is called
  with the full slide list today; grouping slides and calling it per group
  with distinct markers is the only change (see `docs/SERVICENOW.md`).
  Candidate signals: section headers in `original_text`, a `topic` field added
  to `SlideDescription` and the prompt, or manual grouping in the UI.
* **Other document types** (PDF, DOCX): `convert_pptx_to_pdf` already handles
  anything LibreOffice can open; add the extension/magic checks in
  `security/upload_validation.py`.
* **Per-user authorization**: add a dependency in `api.py` reading the SSO
  header set by the reverse proxy and store the owner on the job.
* **Different LLM endpoint type** (e.g. Anthropic-style messages API):
  implement the `LLMClient` protocol (`llm/base.py`) and swap
  `JobRunner.client_factory`.
* **Metrics**: `/api/health` exposes basics; Prometheus can be added without
  enabling the FastAPI telemetry module (keep it off — see security review D1).

## Known limitations

* The web UI lists all jobs for everyone who can reach it (see security review §6).
* Slide notes are extracted and shown in the UI but are not sent to the model
  or included in the article by default (they often contain presenter remarks).
  Include them by adding `s.notes_text` to the hint in `pipeline/processor.py`.
* Animations/builds are flattened by LibreOffice: a slide with staged bullets is
  rendered in its final state.
* Hebrew in the *legacy* `.ppt` binary format depends on LibreOffice's import
  filter quality; PPTX is recommended.

## v1.1 decisions (embedded images, quality validation)

* **Extraction is deterministic, not model-based.** Pictures come from the
  PPTX package (`python-pptx`), so what is attached is exactly what the author
  embedded. The model never decides which image to attach; it only writes the
  text. Vector pictures, OLE objects, shapes and SmartArt have no raster
  representation in the file, so they are reported as *unsupported* rather
  than re-created from a screenshot — the requirement forbids silent
  full-slide fallbacks.
* **Filtering errs on the side of inclusion.** Exclusion requires strong,
  largely independent signals (repetition across slides, degenerate shape,
  uniform colour, background role, sub-1 % placement). A score ≥ 0 keeps the
  picture. Small icons are therefore kept unless they repeat; a reviewer can
  always exclude them, whereas a silently dropped screenshot would go unnoticed.
* **Headings and file names prefer the PPTX title** over the model's title:
  it is the author's wording, it is stable across retries, and it makes the
  mapping slide → section → `NNN_title_KK.png` → attachment obvious.
* **Validation is a gate, not a judge of style.** It only catches the failure
  modes that make a section unusable (no JSON, truncated, loops, empty,
  appearance-only, copied OCR, duplicate of the neighbour). Everything else is
  left to the reviewer, who sees the warnings. A slide that fails after the
  corrective retry is `needs_review`; it is never re-run automatically on
  resume (that would loop on a model that cannot do better) and it blocks
  publishing until a person accepts it.
* **Per-presentation image mode** with a persistent default: the default
  (`embedded`) is right for authored decks with screenshots; `full_slide`
  remains for decks whose content is drawn with shapes/SmartArt, where the
  render is the only faithful picture.
* **Old presentations** (processed by 1.0) are not migrated eagerly; their
  images are extracted lazily on publish or when the mode is re-selected.
  Their article bodies are only rewritten when the user publishes again.
